# Google Meet の受信パケロス — TV の Wi-Fi Direct とメッシュバックホールのエアタイム競合

2026-09-04 調査。[../wifi7-mlo-packetloss.md](../wifi7-mlo-packetloss.md) の MLO 件とは
**別の原因**（あちらの対処は有効なまま）。

## 症状

- wk2511058 で Google Meet が断続的に破綻。**同じネットワークでも Android から参加すると快適。**
- 有線 (USB NIC / 1Gbps) に切り替えても解消しなかった。
- ping・mtr・スループット試験のいずれにも一切現れない。

## 結論

**TV（受信機と画面が無線接続されるタイプ）の Wi-Fi Direct と、AiMesh の無線バックホールが
同じ 80MHz ブロックでエアタイムを奪い合っていた。**

```
TV   (Wi-Fi Direct)  ch40 (5200MHz)  ─┐
                                      ├─ 80MHz 幅なら ch36-48 は同一ブロック
Mesh (backhaul/AP)   ch48 (5240MHz)  ─┘
```

ラップトップの全パケットはこのバックホールを通る。Android は親ルーターに直接繋がっており
バックホールを通らないため無傷だった。これが「Android だけ快適」の答え。

```
ラップトップ → AX86Uノード →【無線バックホール = TVと競合】→ 親ルーター → 外
Android      → 親ルーター（直接）→ 外
```

## 対処

**親ルーター (RT-BE18000) の 5GHz を ch100 固定 / 帯域上限 80MHz（160MHz 無効）。**
AiMesh なのでノード (RT-AX86U) も自動追随する。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 制御チャンネル | 自動（実際は ch48） | **100** |
| 帯域幅 | 20/40/80/160 MHz | **20/40/80 MHz**（160MHz のチェックを外す） |

占有は 5490-5570MHz となり、TV (5170-5250) と完全に分離。気象レーダー帯 (5590-5650) にも触れない。

### なぜ 160MHz を無効にする必要があるか

160MHz のブロックは 5GHz に 2 つしかなく、**どちらも地雷**。

```
ch36-64   (5170-5330)  ← TV の ch40 を丸ごと含む
ch100-128 (5490-5650)  ← 気象レーダー帯 (ch120-128) を丸ごと含む
```

さらに 160MHz はブロック内のどこか一箇所でレーダーを検出しただけで全体を明け渡すため、
DFS の被弾面積が倍になる。バックホールに必要なのはピーク速度ではなく安定性。
**狭くなる方向は安全なので、上限さえ 80MHz に抑えればよい**（自動のままで可）。

## 効果（実測）

| | 通話2 (ch48, TV視聴中, 19.1分) | 通話4 (ch100, 5.6分) |
| --- | --- | --- |
| 映像 損失 | 17.08% | **0.00%**（11,879 受信中 0） |
| 映像 freeze | 132回 / 337.5秒（通話の29%） | **2回 / 1.3秒（0.4%）** |
| 映像 nack | 7038 | **0** |
| 音声 損失 | 16.5〜17.6% | 1.38% |
| 損失が発生した秒 | 189/1146 = 16% | 3/324 = 0.9% |

通話4 の損失は **t=69〜91秒の単発イベント1回のみ**。それ以降は音声を +10,133 パケット
受信して損失 0（0.000%）。連続的な劣化は消えた。

スループットも改善（JAIST から 100MB: 174 → 311 Mbps）。160MHz を切ったことによる
実効速度の低下は観測されなかった。

## 残課題

- **t=69〜91秒の 22 秒イベントの正体は不明。** 送受信が同時に劣化しているので短時間の RF 事象。
  DFS のレーダー退避ではない（ch100 を維持、CSA ログなし）。頻発するようなら再調査。
- **恒久対策は AX86U まで LAN を引くこと。** チャンネル分離は競合を「避けた」対症療法であり、
  TV の設定変更や無線機器の増加で再発しうる。バックホールが有線になれば競合の余地が消える。
- 代替案: AiMesh バックホールを 2.4GHz に逃がす（TV は 5GHz なので競合が消え、DFS も踏まない。
  帯域は落ちるが Meet に必要なのは数 Mbps）。

## この過程で入れた設定（本件の対策ではない）

`modules/network-tuning.nix` の `net.core.rmem_*` は、当初 `Udp6RcvbufErrors` を疑って入れたもの。
**後の測定で、17% ロスの最中 121 秒間の増分が 0 であることを確認しており、本件の対策ではない。**
無害なので残してある。
