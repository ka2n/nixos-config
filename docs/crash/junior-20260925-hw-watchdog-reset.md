## 症状

- 気付くと GUI が消えて CUI のログイン画面になっている
- 実際には **GUI が落ちているのではなく、マシンごと再起動している**。再起動後に greetd + tuigreet（TUI）のログイン画面が出るため CUI に見える
- journal が定常ログの途中で突然途切れ、シャットダウンシーケンスが無い
- `last -x` でそのブートが `still running`（shutdown 記録なし）のまま残る
- journal に残る最古の 2026-06-09 から既に発生している。カーネル 7.0.9 / 7.0.10 / 7.1.2 / 7.1.4 / 7.1.8 のすべてで起きており、特定のカーネル更新による退行ではない
- 2026-07-19〜08-19 の約30日連続稼働のような長い無事故期間もある
- 以前 Arch Linux で運用していた頃（2022〜2023）は問題が無かったとのこと。当時の BIOS / カーネルは未確認

## 確定していること

1. **カーネル panic は起きていない**
   - ramoops を導入し、`echo c > /proc/sysrq-trigger` の強制 panic で**リセットを跨いで記録が残ることを実機で検証済み**（`dmesg-ramoops-0` 111 KB が残った）
   - その上で 09-25・09-28 のクラッシュ後、pstore は空だった（`systemd-pstore.service` が `ConditionDirectoryNotEmpty=/sys/fs/pstore` 不成立でスキップ）
   - ウォッチドッグによるリセット後のブートでは `ramoops: uncorrectable error in header` が0件で、予約領域は壊れずに残っていた。記録が無いのは書かれなかったからであって、消えたからではない

2. **リセットを実行したのは sp5100 TCO ハードウェアウォッチドッグ**
   - `cat /sys/class/watchdog/watchdog0/bootstatus` → `32`（`WDIOF_CARDRESET` = ウォッチドッグが CPU をリセットした）。`wdctl` の表には出ないので raw の sysfs を読む必要がある。通常の再起動後は `0` になることも確認済みで、値は毎回のリセット原因を反映している
   - タイミングが一致: 09-25 は最終ログ 08:42:47、次ブートのカーネル開始 08:46:00 から firmware 17.0s + loader 5.4s（`systemd-analyze`）を引くとリセットは 08:45:36。systemd の最終 ping からちょうど 180 秒（当時の設定値）
   - watchdog を 60s → 180s → 600s と伸ばすたびに、「最終ログ〜リセット」の間隔も伸びた

3. **電源断ではない**: チップセットは通電したまま TCO タイマが数え切っている

4. **CPU ごと完全に止まっている（D-state / IO 待ちのハングではない）**
   - watchdog を 600s にした状態で、09-28 に2回クラッシュ。止まってからリセットまで 5.6 分 / 9.6 分かかった
   - その間、ブロックしたタスクを 120〜240 秒で報告するはずの `hung_task_panic` も発火しなかった。タスクが IO で詰まっただけならカーネルは動いているので、hung_task が panic させて ramoops に記録が残るはず
   - softlockup / hardlockup 検出（`NMI watchdog: Enabled` 確認済み）も無反応

5. **ハードウェアエラーの記録なし**: BERT / APEI / GHES / MCE / thermal いずれも無し。amdgpu のエラー（ring timeout, GPU reset, VM fault）もゼロ

6. **GPU / コンポジタの利用有無は決め手にならない**: クラッシュ 12 回のうち 4 回は river セッションが一度も起動していない（greeter のまま）。クラッシュ間隔も river の有無で差が無い

7. **BIOS 更新（1.M0 → 1.S3）では直らない**: 更新から約5.2時間後の 09-29 15:39 に、同じ形（記録なし、`bootstatus=32`、最終ログの約9.5分後にリセット）で再びクラッシュした

## 確定していないこと

## 次のクラッシュ時の確認手順

**判定に pstore の有無を使わないこと。** このクラッシュは pstore を空のまま残すので、空であることは「落ちていない」を意味しない。

```bash
last -x | head                                    # 非カレントのブートが still running なら異常終了
sudo ls -la /var/lib/systemd/pstore/              # 新しい dmesg-ramoops-* があるか
cat /sys/class/watchdog/watchdog0/bootstatus      # 32 ならウォッチドッグによるリセット
journalctl -b -1 -n 30                            # 最終ログの時刻
systemd-analyze                                   # firmware + loader 時間（リセット時刻の逆算用）
```

`bootstatus` はそのブートの間ずっと同じ値を返すので、**クラッシュ後の再起動で読んだ値かどうか**で判断する。

| 結果 | 意味 |
|---|---|
| `dmesg-ramoops-*` あり | panic した。その dmesg が原因を示す（これまでに無かったパターン） |
| 記録なし、`bootstatus=32`、最終ログ〜リセットが 5〜10 分 | これまでと同じ完全停止。今の対策は効いていない |

## 対策案（1変数ずつ）

1. ~~**BIOS 更新**~~（09-29 実施、**効果なし**）: 1.M0 から 1.S3 までの間に AGESA 1.2.0.B / 1.2.0.Cc / 1.2.0.F / 1.2.0.12 と、Sinkclose などのセキュリティ修正が入っている。アイドル時のフリーズを直したと明記している版は無かった。セキュリティ修正のために 1.S3 のまま据え置く
2. **`processor.max_cstate=1`**（**評価中**、09-29 23:25〜）: CPU が深いアイドル状態（C2）に入らないようにする。アイドル時の消費電力が増える。効いていれば、BIOS の **Power Supply Idle Control → Typical Current Idle** に置き換えられるか試す価値がある（OS 側の制限より影響範囲が狭い。ただし 1.S3 の BIOS 画面では項目が見つかっていない）
3. **GPU の切り分け**: amdgpu を外してヘッドレスで稼働させる。greeter 状態でも落ちているので優先度は低い

> **Note**: 「しばらく落ちない＝直った」と判断するには時間がかかる。直近のペースなら2週間持てば有力な手がかりだが、過去に 10.8 日・約 30 日の無事故連続稼働が実在するので、確信を持つには約1ヶ月見ること。
