## 症状

- 気付くと GUI が消えて CUI のログイン画面になっている
- 実際には **GUI が落ちているのではなく、マシンごと再起動している**。再起動後に greetd + tuigreet（TUI）のログイン画面が出るため CUI に見える
- journal が定常ログの途中で突然途切れ、シャットダウンシーケンスが無い
- `last -x` でそのブートが `still running`（shutdown 記録なし）のまま残る
- 2026-07-19〜08-19 は約30日連続稼働していたが、08-24 以降は1〜5日おきに発生

## 確定していること

1. **カーネル panic は起きていない**
   - ramoops を導入し、`echo c > /proc/sysrq-trigger` の強制 panic で**リセットを跨いで記録が残ることを実機で検証済み**（`dmesg-ramoops-0` 111 KB が残った）
   - その上で 09-25 08:42 のクラッシュ後、pstore は空だった（`systemd-pstore.service` が `ConditionDirectoryNotEmpty=/sys/fs/pstore` 不成立でスキップ）

2. **リセットを実行したのは sp5100 TCO ハードウェアウォッチドッグ**
   - `cat /sys/class/watchdog/watchdog0/bootstatus` → `32`（`WDIOF_CARDRESET` = ウォッチドッグが CPU をリセットした）。`wdctl` の表には出ないので raw の sysfs を読む必要がある
   - タイミングが一致: 最終ログ 08:42:47、次ブートのカーネル開始 08:46:00 から firmware 17.0s + loader 5.4s（`systemd-analyze`）を引くとリセットは **08:45:36**。systemd の最終 ping からちょうど 180 秒（当時の設定値）
   - watchdog を 60s → 180s にしたら「最終ログ〜リセット」の間隔が約 92 秒 → 約 169 秒に伸びた

3. **電源断ではない**: チップセットは通電したまま TCO タイマが 180 秒を数え切っている

4. **ハードウェアエラーの記録なし**: BERT / APEI / GHES / MCE / thermal いずれも無し。amdgpu のエラー（ring timeout, GPU reset, VM fault）もゼロ

5. **GPU / コンポジタの利用有無は決め手にならない**: クラッシュした 10 ブートのうち 3 つは river セッションが一度も起動していない（greeter のまま）。クラッシュ間隔も river あり平均 約1.5日 / なし 約1.8日 で差が無い

## 確定していないこと

- **「CPU が完全に止まった」のか「D-state / IO 待ちでハングした」のか判別できていない**
  - softlockup / hardlockup 検出は **CPU がスピンしている時にしか発火しない**。IO 待ちや fence 待ちで CPU がアイドルなら元々出ないので、出なかったことは証拠にならない
  - D-state ハングを拾う唯一の検出器は `hung_task_panic` だが、`hung_task_check_interval_secs=0` なので khungtaskd は 120 秒ごとにしかスキャンせず、報告はブロックから **120〜240 秒後**になる
  - 一方、watchdog は systemd が `runtimeTime/2` ごとに ping するため、フリーズの **`runtimeTime/2`〜`runtimeTime` 後**にリセットする。180s 設定では 90〜180 秒後で、**hung_task より先にリセットし得た**
  - → 600s に引き上げて判別可能にした（下記）
- **アイドル時に偏るかどうか**: 発生時刻はばらばらで、作業中かどうか不明なものが多い

## 次のクラッシュ時の確認手順

**判定に pstore の有無を使わないこと。** このクラッシュは pstore を空のまま残すので、空であることは「落ちていない」を意味しない。

```bash
last -x | head                                    # 非カレントのブートが still running なら異常終了
sudo ls -la /var/lib/systemd/pstore/              # 新しい dmesg-ramoops-* があるか
cat /sys/class/watchdog/watchdog0/bootstatus      # 32 ならウォッチドッグによるリセット
journalctl -b -1 -n 30                            # 最終ログの時刻
systemd-analyze                                   # firmware + loader 時間（リセット時刻の逆算用）
```

`bootstatus` はそのブートの間ずっと同じ値を返す。現在の 32 は 9/25 08:45 のリセットを指しているので、**次のクラッシュ後に読んだ値かどうか**で判断する。

| 結果 | 意味 | 次の一手 |
|---|---|---|
| `dmesg-ramoops-*` あり | **D-state ハング** | hung_task のバックトレースが nvme / btrfs / dma_fence / amdgpu のどれを指すかで対象を絞る |
| 記録なし、最終ログ〜リセットが 5〜10 分 | **真の完全停止** | 下記の候補を1つずつ試す |

## 対策案（切り分け後に1変数ずつ）

完全停止だった場合の候補:

1. **Zen 2 のアイドル時ハング**: BIOS の Power Supply Idle Control を Typical Current Idle にする、または `processor.max_cstate=1`。CPU は cpu0 で稼働時間の約 98% を C2 で過ごしているので、仮説として除外はできない（ただし確定もしていない）
2. **BIOS 更新**: MSI の MS-7C35 サポートページで 1.M0 より新しいものがあるか要確認（未確認）
3. **GPU の切り分け**: amdgpu を外してヘッドレスで稼働させる

> **Note**: 「しばらく落ちない＝直った」と判断するには**約1ヶ月**必要。過去に 10.8 日・約 30 日の無事故連続稼働が実在するため、1週間程度の無事故では何も証明できない。
